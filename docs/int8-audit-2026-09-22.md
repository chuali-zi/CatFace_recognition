# INT8 QDQ 审计（2026-09-22）

## 结论

现有 `baseline-int8/model.onnx` 的低相似度（量化报告实际只对校准样本前 10 张计算 cosine，均值为 0.2756，最低为 0.2155；100 是校准总数）不能归因于两个 SE 分支 ReLU 的 `scale=1.0`。进一步把这两个中间张量暴露为图输出后，在 metadata 记录的校准样本前 3 张上，FP32/preprocessed 图的两个 ReLU 输出均为全零；INT8 图中对应的 ReLU 和其 QDQ 后浮点张量也均为全零。因此这里是合法的 zero-range/default 表示，不是“非零激活被 scale=1 舍入清零”的已定位错误。

`scale=1.0` 仍值得在更多校准图上记录，但当前证据不支持为它做排除量化实验，也不支持把它当作 cosine 崩溃的根因。低 cosine 的具体原因仍未确定；优先级应转向其他中间 QDQ/算子或校准覆盖诊断，而不是重选模型路线。

## 证据

- FP32 `baseline/model.onnx`：125 节点，52 Conv、18 HardSwish、14 Relu；模型 metadata 的 5 张真实图 parity 为 max absolute error `5.07e-7`、min cosine `0.99999994`。
- `baseline-int8/model.preprocessed.onnx`：预处理只把 HardSwish 展开成 HardSigmoid+Mul（18 个 HardSwish 变为 27 个 HardSigmoid/27 个 Mul），未见删除主干或输出归一化的证据。
- INT8 `model.onnx`：52 个 Conv 均带 QDQ；输出端仍保留 `GlobalAveragePool -> Flatten -> ReduceL2 -> Div`，embedding 本身没有被再次整数量化。因此问题更可能发生在主干中间层，而不是最终 L2/余弦计算。
- 两个 SE 中间点的量化参数如下（均为 per-tensor activation QDQ）：

  | 张量 | 前一层 FC1 Conv scale | ReLU scale / zero point | 后一层 FC2 Conv scale |
  | --- | ---: | ---: | ---: |
  | `features.1/block/block.1` | `6.888866e-05`, zero point `127` | **`1.0`, `0`** | `0.00977569`, zero point `-12` |
  | `features.4/block/block.2` | `0.03980691`, zero point `127` | **`1.0`, `0`** | `0.01236041`, zero point `25` |

- 对比其余 SE FC1 ReLU，scale 约为 `0.01146`–`0.01874`（以及早期普通 ReLU 的 `0.015`–`0.0556`），但 scale 离群本身不能证明错误。诊断结果保存在 `experiments/runs/gallery-study/quant-probe/three.json`，探针代码为 `experiments/identity/quantization_probe.py`。
- 3 张已有 clean 图只做了读取和推理对照（未重新校准）：FP32/INT8 embedding cosine 分别为 `0.2875`、`0.2338`、`0.2359`；两边 embedding norm 都约为 1。这说明最终归一化数值稳定，但不能由这 3 张图定位主干中的具体失真点。
- 输入 `image_scale=0.01865845`、zero point `-14`，按 `(q - zero_point) * scale` 和 int8 的 `[-128, 127]` 计算，对应约 `[-2.127, 2.631]` 的输入覆盖；metadata 规定的 `/255` 加 ImageNet mean/std 与此量级一致，当前证据不能把预处理范围不一致作为主因。
- 原始 FP32 `baseline/model.onnx` 与 `model.preprocessed.onnx` 在 3 张样本上的最终 embedding cosine 为 `0.99999982`、`0.99999958`、`0.99999976`，最大绝对差为 0；52 个 Conv 中间输出的相对 L2 差也为 0。这排除了 `quant_pre_process` 本身改变数值图的解释。
- 直接比较语义相同的激活后，首层 HardSwish 的相对 L2 约 `0.094`、cosine 约 `0.996`；其后的 `features.1/block/block.0/block.0.2/Relu`（depthwise Conv 后的 Relu）相对 L2 约 `0.517`–`0.629`、cosine 约 `0.855`–`0.887`。因此此前把 Conv pre-activation 与 QDQ/post-activation 混比的 `.641` 不能作为独立误差源；但 depthwise 后的语义相同激活确实已明显偏离。结果见 `three.json` 的 `activation_comparison`。
- 52 个量化 Conv 权重的 per-channel scale 长度均等于权重 shape 的第 0 轴（包括 depthwise Conv），未发现轴长度错配；没有零 scale。仅凭 scale 范围不能证明权重误量化。
- 对应 `features.1` depthwise Conv 权重反量化后相对 L2 误差约 `0.0041`，没有异常大的权重误差；其 bias 在量化图中保持浮点 initializer。3 张图的输入量化饱和率均为 `0/76800`，所以当前证据不支持输入 clipping 或该 depthwise 权重轴错误是根因。

## HardSwish、输出和优化边界

图中 HardSwish 的显式形式是 `HardSigmoid(x) -> Mul(x, ...)`，这是预处理后的正常展开；没有证据表明 ORT 把 HardSwish 错接成了别的算子。最终 `ReduceL2`、`Expand`、`Div` 仍是浮点输出路径，未见“输出被极小 clip 量化”这一现象。

这里仍不能证明 ORT 的根本 bug，也没有证据说明 per-channel 权重量化本身异常；权重 scale 虽跨通道变化很大，但没有零 scale。当前尚未输出所有校准张量的逐层浮点/量化误差，因此不能把低 cosine 归因到某个具体 operator。

## 优先级建议

1. 不要把这两个 `scale=1.0` 的 SE ReLU 当作已确认 bug，也不要为它们单独排除量化。
2. 若继续调查，应在同一校准集上逐层收集 FP32/preprocessed 与 INT8 中间张量的误差，优先查非零范围且误差异常的 QDQ 或算子；本轮没有足够证据再做量化实验。
3. 所有 INT8 结论仍需重新阈值校准并按身份指标评测；本报告的 cosine 只说明图级输出差异，不等于门口识别率。
